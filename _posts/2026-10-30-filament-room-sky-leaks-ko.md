3D 방에서 쫓아다닌 흰 면은 전부 하늘이었다. 처음엔 하늘이 방 안 전체를 비췄다. 다음엔 원래 없던 벽 자리로 하늘이 보였고 마지막엔 그림자를 끄라고 해 둔 벽을 해가 그대로 뚫고 들어왔다. 뒤의 두 번은 카메라를 끄는 동안에만 나타나서 하네스 스크린샷에는 한 번도 찍히지 않았다.

## Metal로 그리던 방과 정지 화면 하네스

이 방은 개인 iOS 앱 안에 있다. Blender로 모델링하고 조명을 잡았고, 이번 이식 전까지는 직접 짠 Metal 렌더러가 Cycles로 구운 빛을 얹어 그렸다. 나중에 Android에서도 같은 장면을 쓰려고 Filament 1.79.0으로 옮겼고 iOS에는 Objective-C++ 브리지로 붙였다. 방 크기는 4m 안팎이다. 아래 기기 수치는 iPhone 13에서, 시뮬레이터 수치는 iOS 26.5 iPhone 17 Pro 시뮬레이터에서 쟀다. 빌드는 모두 Mac 한 대에서 했다.

앱 옆에는 Mac 오프스크린 하네스를 두었다. 앱과 같은 GLB, 조명 값을 모아 둔 같은 C++ 헤더로 낮과 밤 PNG를 뽑는다. 나는 이 캡처를 앱 화면 대신 믿었다.

## 바깥 HDRI가 방 전체를 비췄다

처음엔 뻔한 방법부터 썼다. Blender 장면이 월드에 쓰던 HDRI를 그대로 Filament의 image-based lighting(IBL)으로 넣었다. 깊이감은 생겼지만 바닥과 천장이 희누렇게 날아갔고 월넛 가구는 탁한 보라색이 됐다. 상수 구면 조화(SH) 채움광으로 바꾸면 반대로 모든 게 납작해졌다.

Filament IBL은 무한히 먼 환경을 흉내 낸다. 벽이나 천장은 모른다. 그래서 바깥 하늘이 방 안 모든 면의 확산광과 반사에 섞였고 clearcoat 바닥에는 하늘이 그대로 비쳤다. GTAO가 일부를 가렸지만 턱없이 모자랐다.

방을 바깥처럼 다루는 일부터 그만뒀다. 원본 Blender 낮·밤 조명 리그를 그대로 써서 방 안 한 점에서 Cycles 360° 프로브를 구웠다. 굽는 데 20초쯤 걸린다. 이걸 `cmgen`에 넣어 IBL을 만들었다. HDRI는 창밖에 보이는 skybox로만 남겼고 해는 따로 방향광으로 넣었다. 이제 반사에는 방이 비치고 간접광 색은 원본 GI를 따라간다. 다만 한 점에서 구운 프로브라 자리마다 간접광이 달라지지는 않는다. 그건 다음 단계인 라이트맵이 맡는다.

같은 오후에 작은 함정도 둘 만났다. `AssetLoader::create`에 `NameComponentManager`를 넘기지 않으면 gltfio가 노드 이름을 전부 `nil`로 준다. 그러면 pick을 해도 이름 없는 entity만 잡힌다. Blender glTF 내보내기는 발광을 빼먹고 Generated 텍스처 좌표를 `texCoord: -1`로 쓰는데 gltfio는 이 파일을 로드하지 않는다. 모바일용 GLB는 텍스처를 1024px로 줄이고 Draco로 압축해 48.48MB에서 7.39MB가 됐다.

## 끄는 동안 프레임당 57~86ms

초기 TestFlight 빌드는 끄는 동안에도 매 프레임 SSR·고품질 GTAO(bent normals 켬)·PCSS 소프트 그림자·bloom·TAA를 다 그렸다. iPhone 13에서 프레임당 GPU 시간이 57~86ms 나왔다. 그래서 렌더를 두 단으로 나눴다. 사용자가 끌거나 걷는 동안 쓰는 조작 단이 있고 손을 떼면 돌아가는 정지 단이 있다. 조작 단 첫 버전은 SSR을 끄고 AO를 bent normals 없이 낮은 품질로 내렸으며 동적 해상도를 허용했다. 조작 중 프레임은 14.5ms 안팎으로 내려왔다.

하네스는 계속 정지 단만 그렸다. PNG는 정지 프레임이니까.

## 끌면 하얗고 멈추면 멀쩡했다

다음 TestFlight 빌드에서 화면을 끌어 둘러볼 때마다 큰 흰 면이 보였다. 멈춘 화면은 멀쩡했다.

시뮬레이터에서 ±67° 정도 합성 끌기를 돌리며 화면을 녹화했고 1초 간격으로 프레임을 뽑았다. 왼쪽으로 돌 때마다 화면 왼쪽 절반이 하얗게 번졌다. 의심한 건 근평면(0.05m)·동적 해상도·TAA 이력 리셋, 그리고 텍스처를 비동기로 올리는 동안의 빈 프레임이었다. 녹화 프레임에는 어느 쪽 흔적도 없었다. 로딩 중 검은 프레임은 있었지만 장면이 뜨기 전이었고 흰색도 아니었다.

눈 위치 둘레의 GLB 노드 경계를 찍어 보고서야 알았다. 그쪽에 벽이 없었다. Blender 방은 디오라마다. 카메라 쪽 면을 일부러 비워 두고 그 틈으로 하늘빛이 그늘을 채우게 했다. 카메라가 상자 밖에 서 있다면 맞는 선택이다. 그런데 1인칭 시작 자리가 그 열린 면에서 0.35m 떨어져 있었다.

```
   위에서 본 방               뒷벽
            +-----------------------------+
   창 쪽    |                             |
   벽  ->   |             방              |
   (해)     |                             |
            |                    눈 *     |
            +  -  -  -  -  -  -  -  -  -  +   <- 눈에서 0.35m, 벽 없음
                     낮 HDRI skybox            (해도 이쪽에서 비스듬히 든다)
```

왼쪽이나 뒤로 돌면 밝은 낮 하늘이 화면을 채웠다. Metal 버전에서 이게 안 보인 건 방이 더 큰 장면 안에 놓여 그 면이 닫혀 있었기 때문이다.

이제 내보내기 스크립트가 앞벽을 더한다. 해가 그쪽에서 들어오니 앞벽이 그림자를 드리우면 원본보다 방이 어두워진다. 나는 빛을 원본 그대로 두려고 새 벽의 그림자를 껐다. 이전 캡처와 비교한 정지 화면 PSNR은 낮 84dB, 밤 81dB였다. 같은 끌기를 다시 녹화하자 흰 번짐이 사라졌다. iPhone 13에서 조작 단 GPU p50을 세 번 재니 14.3·14.2·15.3ms였다. 그 전에 잰 14.3·14.5ms와 같은 범위라서 앞벽 한 장이 조작 단 비용을 바꾸지는 않았다.

## 조작 단을 11ms까지 깎다

p50 14.5ms는 여전히 예산 12ms를 넘었다. 게다가 그 예산은 p95 기준이다. 한 시간 뒤 조작 단을 더 깎았다. PCSS 대신 PCF 그림자를 쓰고 AO와 bloom·TAA를 껐다. 그림자 캐스케이드는 1개, 그림자 맵은 1024로 줄였고 접촉 그림자도 껐다. 기기에서 두 번 재니 GPU p50이 11.0ms와 10.0ms(p95 14.1ms와 13.0ms)였다.

## AO를 끄자 화면이 뿌예졌다

이 변경 뒤로 전환할 때마다 화면 전체가 잠깐 우윳빛이 됐다가 돌아왔다. 카메라가 멈춰 있어도 조작 단으로 그리게 하는 개발용 플래그를 넣어 두 단을 같은 자세에서 찍었다. 각 캡처의 3D 영역을 ffmpeg `ssim`·`signalstats` 필터로 비교했고 정지 단에서 효과를 하나씩 꺼 봤다. 조작 단과 수치가 가장 비슷한 줄을 보면 된다.

| 프레임(같은 자세, 낮) | 정지 단 대비 SSIM | YLOW(어두운 끝) | YAVG |
|---|---|---|---|
| 정지 단 | 1 | 69 | 127.3 |
| 조작 단 | 0.862 | 92 | 137.7 |
| 정지 단, AO만 끔 | 0.906 | 90 | 136.5 |
| 정지 단, SSR만 끔 | 0.979 | 75 | 129.5 |
| 정지 단, TAA만 끔 | 0.953 | 64 | 126.5 |
| 정지 단, PCSS 대신 PCF | 0.988 | 67 | 126.7 |

AO 하나만 꺼도 어두운 쪽이 들뜨는 현상이 거의 다 재현됐다. bent normals를 켠 AO가 IBL이 닿으면 안 되는 곳을 막아 주는데 조작 단에는 그게 없었다. AO를 낮은 품질로 다시 켜고 bent normals도 켜자 SSIM 0.919, YLOW 72가 나왔다. 나는 이 효과 하나만 고치고 넘어갔다. 두 단 사이의 다른 차이는 그대로 뒀다.

## 그림자를 끈 벽으로 110,000 lux 해가 들어왔다

그날 늦게 다른 증상이 나왔다. 걷거나 고개를 돌릴 때 흰 얼룩이 떨렸고 햇빛이 사라졌다 다시 떴다. 이번엔 손대기 전에 무엇을 잴지와 문턱부터 적었다.

- 흰색이든 검은색이든 단색 프레임은 0장.
- 화질 단 전환 깜빡임 0. 평균 휘도 변화가 0.5를 넘거나 8×8 블록 변화가 3을 넘으면(0~255 기준) 깜빡임으로 센다.
- 단 전환 때 그림자 맵이 바뀌는 횟수 0.
- 낮밤 전환 중 한 프레임의 평균 휘도 변화는 8 이하.

0.5는 평균 휘도 130의 약 0.4%다. 수정 뒤 TAA 흔들림(0.15)보다는 크고 수정 전 단 전환(1.55)보다는 작아서 이 값을 골랐다.

하네스는 프레임마다 화면을 읽어 온다. 단이 바뀐 프레임이 두 문턱 중 하나라도 넘게 변했으면 깜빡임으로 센다.

```python
import numpy as np

def is_flicker(prev, cur, mean_limit=0.5, block_limit=3.0):
    """prev, cur: 3D 영역의 휘도(2D uint8), 카메라는 정지."""
    a, b = prev.astype(np.float32), cur.astype(np.float32)
    if abs(b.mean() - a.mean()) > mean_limit:
        return True
    h, w = (a.shape[0] // 8) * 8, (a.shape[1] // 8) * 8
    blocks = lambda x: x[:h, :w].reshape(h // 8, 8, w // 8, 8).mean(axis=(1, 3))
    return np.abs(blocks(b) - blocks(a)).max() > block_limit

flicker = sum(is_flicker(f[i - 1], f[i]) for i in tier_switch_frames)
```

그다음 같은 자세에서 설정을 하나씩 바꿨다. 조작 단의 PCF를 PCSS로 되돌렸을 때만 큰 흰 얼룩이 사라졌다. 얼룩은 내가 그림자를 꺼 둔 앞벽을 그대로 통과한 110,000 lux 해였다. PCSS에서는 우연히 가려졌을 뿐이다. 빛이 벽을 뚫는 게 문제였으니 벽이 빛을 막게 고쳤다.

단이 바뀔 때 화면이 튀는 나머지 몫은 대부분 SSR이 켜졌다 꺼지는 탓이었다. 그 차이 하나만 없애도 전환당 평균 휘도 변화가 1.86에서 0.66으로 줄었다. 남은 몫은 PCSS·그림자 맵 크기·TAA·bloom이 나눠 가졌다.

## 두 단이 다를 수 있는 값은 표 한 곳에만

이번에는 빛을 바꾸는 값이 두 단 사이에서 다르지 않게 했다. 이제 두 단은 AO 품질만 다르고 그 차이는 작은 표 한 곳에만 있다.

```cpp
struct Tier { filament::QualityLevel ao, aoFilter; };   // 허용된 차이는 이것뿐

Tier tierFor(bool moving) {
    using filament::QualityLevel;
    return moving ? Tier{QualityLevel::LOW, QualityLevel::MEDIUM}
                  : Tier{QualityLevel::HIGH, QualityLevel::HIGH};
}

void apply(filament::View* view, const Tier& t) {
    using namespace filament;
    AmbientOcclusionOptions ao;
    ao.bentNormals = true;                 // 가려진 곳에 IBL이 새지 않게
    ao.quality = t.ao;
    ao.lowPassFilter = t.aoFilter;
    view->setAmbientOcclusionOptions(ao);
    view->setShadowType(ShadowType::PCF);  // 두 단 공통
    ScreenSpaceReflectionsOptions ssr;
    ssr.enabled = false;                   // 두 단 공통
    view->setScreenSpaceReflectionsOptions(ssr);
    // TAA·bloom 켬, 동적 해상도 끔, 1024 그림자 맵도 두 단 공통
}
```

나머지는 두 단에 한 번만 설정한다. 앞벽은 이제 그림자를 드리운다. 창 유리와 창 너머 하늘 면만 그림자를 드리우지 않으니 햇빛은 창으로만 든다. 창으로 든 햇빛 자리가 흰색으로 날아가서 해 세기도 110,000에서 50,000 lux로 낮췄다.

## 낮밤 전환과 검은 첫 프레임

낮밤 전환은 t = 0.5에서 프로브를 통째로 바꿨다. 그 한 프레임에서 평균 휘도가 58 뛰었다. 지금은 확산광 SH를 프레임마다 섞고 해 세기는 로그 공간에서 잇는다. 노출이 로그 단위라서 선형으로 섞으면 전환 한가운데가 낮보다 밝아졌다.

```cpp
float3 sh[9];
for (int i = 0; i < 9; ++i) sh[i] = daySH[i] * (1 - t) + nightSH[i] * t;
auto* light = IndirectLight::Builder()
    .reflections(t < 0.5f ? dayCube : nightCube)
    .irradiance(3, sh)
    .build(*engine);
scene->setIndirectLight(light);           // 직전에 섞은 것은 destroy
float sunLux = std::exp(std::lerp(std::log(daySun), std::log(nightSun), t));
```

목록 화면에서 방으로 들어갈 때 0.2초쯤 화면이 새까맸다. 호스트가 첫 프레임을 제출하자마자 화면을 드러낸 탓이다. 프레임을 더 그려 둬도 그대로였다. 첫 프레임의 GPU 시간이 돌아온 뒤에(끝내 안 오면 30장 뒤에) 드러내게 하자 사라졌다.

## 고치기 전과 후

아래 수치는 Mac 하네스(780×1688)와 iPhone 17 Pro 시뮬레이터에서 쟀다.

| 지표 | 전 | 후 |
|---|---|---|
| 단 전환 깜빡임 프레임, 낮 / 밤 | 6 / 4 | 0 / 0 |
| 단 전환당 평균 휘도 변화, 낮 / 밤 | 1.55 / 3.12 | 0.017 / 0.006 |
| 단 전환 때 그림자 맵 변화 | 6 | 0 |
| 한 프레임 최대 변화, 낮→밤 / 밤→낮 | 58.3 / 58.3 | 6.2 / 5.3 |
| 목록↔방 검은 프레임, 전환 4번 | 43 | 0 |
| Metal 기준선 대비 SSIM, 낮 / 밤 | 0.770 / 0.682 | 0.783 / 0.679 |
| Metal 기준선 대비 FLIP, 낮 / 밤 | 0.390 / 0.548 | 0.384 / 0.553 |

시간 안정성 지표는 크게 좋아졌다. 화질 지표는 거의 그대로였고 밤은 두 지표 모두 조금 나빠졌다. SSIM과 FLIP 문턱은 이번 측정을 보고 정했다. 그래서 수정 전 값도 통과한다. 이 문턱은 회귀를 잡을 뿐이고 이식본이 Metal 버전과 같다는 증거가 되지는 못한다. 원래 목표(SSIM ≥ 0.95, FLIP ≤ 0.05)와는 아직 거리가 멀다. 그 차이의 큰 몫은 Metal 버전이 여러 리그로 구운 GI다.

안정성을 얻은 값은 정지 화면이 치렀다. 바닥과 탁자의 화면 공간 반사가 빠졌고 PCSS 소프트 그림자·접촉 그림자·2048 그림자 맵도 빠졌다. 밤 창밖은 여전히 낮처럼 밝고 LED 띠의 빛은 벽에 번지지 않는다. 둘 다 라이트맵 작업에서 다룬다.

## 스크린샷보다 끌기 녹화를 먼저 본다

오프라인 Blender 장면은 무대처럼 만든다. 환경은 배경막이고 카메라가 밖에 서 있으니 벽 하나쯤 없어도 된다. IBL을 쓰는 Filament는 그 환경을 사방에서 오는 빛으로 다루고 1인칭 카메라는 보는 사람을 상자 안에 세운다. 나는 장면을 글자 그대로 옮긴 뒤 옮길 때마다 드러난 구멍을 하나씩 메웠다.

다음에도 쓸 것은 화질 단 쪽이다. 성능 때문에 단을 나눴는데 AO·그림자 필터링·SSR처럼 빛이나 그림자를 바꾸는 값이 단마다 다를 때마다 움직일 때만 생기는 결함이 나왔다. 하네스는 정지 프레임만 찍었다. 그래서 이틀 동안 나는 이미 맞게 나오는 유일한 상태와만 비교하고 있었다. 다음 장면에서는 위의 단 표를 첫 커밋에 넣겠다. 그리고 스크린샷을 믿기 전에 단이 바뀌는 대본 끌기를 하네스로 녹화해 깜빡임 판정부터 돌리겠다.
