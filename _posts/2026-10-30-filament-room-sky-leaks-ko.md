3D 방에서 쫓아다닌 흰 면은 알고 보니 전부 하늘이었다. 처음에는 하늘빛이 방 안 전체를 비췄고, 다음에는 원래 없던 벽 자리로 하늘이 보였다. 마지막에는 그림자를 드리우지 않게 설정해 둔 벽을 햇빛이 그대로 뚫고 들어왔는데, 뒤의 두 번은 카메라를 드래그하는 동안에만 나타나서 하네스 스크린샷에는 한 번도 찍히지 않았다.

## Metal 렌더러와 정지 화면 하네스

이 방은 개인 iOS 앱 안에 있다. Blender로 모델링하고 라이팅을 잡았으며, 이번에 옮기기 전까지는 직접 짠 Metal 렌더러가 Cycles로 베이크한 빛을 얹어 그렸다. 나중에 안드로이드에서도 같은 장면을 쓰려고 Filament 1.79.0으로 옮겼고, iOS에는 Objective-C++ 브리지로 붙였다. 방 크기는 4m 안팎이다. 아래 기기 수치는 iPhone 13에서, 시뮬레이터 수치는 iOS 26.5 iPhone 17 Pro 시뮬레이터에서 측정했고 빌드는 모두 Mac 한 대에서 했다.

앱 옆에는 Mac 오프스크린 하네스를 두었다. 앱과 같은 GLB, 그리고 조명 값을 모아 둔 같은 C++ 헤더로 낮과 밤 PNG를 뽑는 도구인데, 나는 이 캡처가 앱 화면과 같다고 믿었다.

## 바깥 HDRI로 방 전체가 밝아지는 문제

처음에는 뻔한 방법부터 썼다. Blender 장면이 월드에 쓰던 HDRI를 그대로 Filament의 IBL(이미지 기반 라이팅)로 넣었더니 깊이감은 생겼지만 바닥과 천장이 희누렇게 날아갔고 월넛 가구는 탁한 보라색이 됐다. 반대로 상수 SH(구면 조화 함수) 앰비언트 라이트로 바꾸면 모든 것이 납작해 보였다.

Filament의 IBL은 무한히 먼 환경을 가정하므로 벽이나 천장이 있다는 사실을 모른다. 그래서 바깥 하늘이 방 안 모든 면의 디퓨즈와 스페큘러에 섞였고, clearcoat 바닥에는 하늘이 그대로 비쳤다. GTAO가 일부를 가려 주긴 했지만 턱없이 모자랐다.

결국 방을 바깥처럼 다루는 것부터 그만뒀다. 원본 Blender의 낮·밤 조명 리그를 그대로 써서 방 안 한 점에서 Cycles 360° 프로브를 베이크했는데, 한 번에 20초쯤 걸린다. 이걸 `cmgen`에 넣어 IBL을 만들고, HDRI는 창밖에 보이는 스카이박스로만 남겼으며 해는 따로 디렉셔널 라이트로 넣었다. 이제 반사에는 방이 비치고 간접광 색도 원본 GI를 따라간다. 다만 한 점에서 베이크한 프로브라서 자리마다 간접광이 달라지지는 않는데, 이 부분은 다음 단계인 라이트맵 작업에서 다룰 예정이다.

같은 날 오후에는 작은 함정에도 두 번 걸렸다. `AssetLoader::create`에 `NameComponentManager`를 넘기지 않으면 gltfio가 노드 이름을 전부 `nil`로 돌려주므로, 피킹을 해도 이름 없는 entity만 잡힌다. 또한 Blender의 glTF 내보내기 기능은 이미션을 빼먹고 Generated 텍스처 좌표를 `texCoord: -1`로 쓰는데, gltfio는 이 파일을 로드하지 않는다. 모바일용 GLB는 텍스처를 1024px로 줄이고 Draco로 압축해서 48.48MB에서 7.39MB로 줄일 수 있었다.

## 드래그 중 프레임당 57~86ms

초기 TestFlight 빌드는 드래그하는 동안에도 매 프레임 SSR, 고품질 GTAO(bent normals 켬), PCSS 소프트 섀도, 블룸, TAA를 모두 그렸다. 그 결과 iPhone 13에서 프레임당 GPU 시간이 57~86ms 나왔다. 그래서 품질 설정을 둘로 나눴다. 사용자가 드래그하거나 걷는 동안에는 '이동 중 품질'로 그리고, 손을 떼면 '정지 품질'로 돌아간다. 이동 중 품질의 첫 버전은 SSR을 끄고 AO를 bent normals 없이 낮은 품질로 내렸으며 동적 해상도를 허용했는데, 이것만으로 이동 중 프레임이 14.5ms 안팎까지 내려왔다.

하지만 하네스는 계속 정지 품질만 그렸다. PNG는 정지 프레임이기 때문이다.

## 드래그할 때만 보이는 흰 면

다음 TestFlight 빌드에서 화면을 드래그해 둘러볼 때마다 큰 흰 면이 보였는데, 멈춘 화면은 멀쩡했다.

시뮬레이터에 ±67° 정도 회전하는 드래그 입력을 스크립트로 넣으며 화면을 녹화했고, 1초 간격으로 프레임을 뽑아 보니 왼쪽으로 돌 때마다 화면 왼쪽 절반이 하얗게 번졌다. near plane(0.05m), 동적 해상도, TAA 히스토리 리셋, 텍스처를 비동기로 올리는 동안의 빈 프레임을 의심했지만 녹화 프레임에는 어느 쪽 흔적도 없었다. 로딩 중 검은 프레임은 있었지만 장면이 뜨기 전이었고 흰색도 아니었다.

### 흰 면은 어디서 왔나

눈 위치 주변의 GLB 노드 경계를 찍어 보고서야 그쪽에 벽이 없다는 것을 확인했다. Blender 방은 디오라마라서 카메라 쪽 면을 일부러 비워 두고 그 틈으로 하늘빛이 그늘을 채우게 만들었는데, 카메라가 상자 밖에 서 있다면 맞는 선택이다. 그런데 1인칭 시작 위치가 그 열린 면에서 0.35m밖에 떨어져 있지 않았다.

```
   위에서 본 방               뒷벽
            +-----------------------------+
   창 쪽    |                             |
   벽  ->   |             방              |
   (해)     |                             |
            |                    눈 *     |
            +  -  -  -  -  -  -  -  -  -  +   <- 눈에서 0.35m, 벽 없음
                     낮 HDRI skybox            (해도 이쪽에서 비스듬히 든다)
```

그래서 왼쪽이나 뒤로 돌면 밝은 낮 하늘이 화면을 채웠다. Metal 버전에서 이게 보이지 않았던 것은 방이 더 큰 장면 안에 놓여 그 면이 닫혀 있었기 때문이다.

지금은 내보내기 스크립트가 앞벽을 추가한다. 해가 그쪽에서 들어오므로 앞벽이 그림자를 드리우면 원본보다 방이 어두워지는데, 빛을 원본 그대로 두려고 새 벽의 그림자를 껐다. 이전 캡처와 비교한 정지 화면 PSNR은 낮 84dB, 밤 81dB였고, 같은 드래그를 다시 녹화하자 흰 번짐이 사라진 것을 확인했다. iPhone 13에서 이동 중 품질의 GPU p50(중앙값)을 세 번 측정하니 14.3·14.2·15.3ms였다. 그 전에 잰 14.3·14.5ms와 같은 범위이므로 앞벽을 추가해도 이동 중 비용은 달라지지 않았다.

## 이동 중 품질을 11ms로 줄이기

그래도 p50 14.5ms는 프레임 예산 12ms를 넘었고, 게다가 그 예산은 p95 기준이다. 그래서 한 시간 뒤 이동 중 품질을 더 낮췄다. PCSS 대신 PCF 그림자를 쓰고 AO와 블룸·TAA를 껐으며, 섀도 캐스케이드는 1개, 섀도 맵은 1024로 줄이고 컨택트 섀도도 껐다. 기기에서 두 번 측정하니 GPU p50이 11.0ms와 10.0ms(p95 14.1ms와 13.0ms)로 내려왔다.

## AO를 끈 뒤 뿌옇게 뜨는 화면

이 변경 뒤로는 품질이 바뀔 때마다 화면 전체가 잠깐 우윳빛이 됐다가 돌아왔다. 카메라가 멈춰 있어도 이동 중 품질로 그리게 하는 개발용 플래그를 넣어, 두 품질 설정을 같은 자세에서 찍었다. 각 캡처의 3D 영역을 ffmpeg `ssim`·`signalstats` 필터로 비교하면서 정지 품질에서 효과를 하나씩 꺼 봤다. 아래 표에서는 이동 중 품질과 수치가 가장 비슷한 줄을 찾으면 된다.

| 프레임(같은 자세, 낮) | 정지 품질 대비 SSIM | YLOW(어두운 끝) | YAVG |
|---|---|---|---|
| 정지 품질 | 1 | 69 | 127.3 |
| 이동 중 품질 | 0.862 | 92 | 137.7 |
| 정지 품질, AO만 끔 | 0.906 | 90 | 136.5 |
| 정지 품질, SSR만 끔 | 0.979 | 75 | 129.5 |
| 정지 품질, TAA만 끔 | 0.953 | 64 | 126.5 |
| 정지 품질, PCSS 대신 PCF | 0.988 | 67 | 126.7 |

AO 하나만 꺼도 어두운 쪽이 들뜨는 현상이 거의 그대로 재현됐다. bent normals를 켠 AO가 IBL이 닿으면 안 되는 곳을 막아 주는데, 이동 중 품질에는 그게 빠져 있었다. AO를 낮은 품질로 다시 켜고 bent normals도 켜자 SSIM 0.919, YLOW 72가 나왔다. 나는 이 효과 하나만 고치고 넘어갔고, 두 품질 설정 사이의 다른 차이는 그대로 뒀다.

## 그림자를 끈 벽으로 들어온 110,000 lux 햇빛

그날 늦게 또 다른 증상이 나왔다. 걷거나 고개를 돌릴 때 흰 얼룩이 떨렸고, 햇빛이 사라졌다가 다시 나타났다. 이번에는 손대기 전에 무엇을 측정할지와 임계값부터 적었다.

- 흰색이든 검은색이든 단색 프레임은 0장.
- 품질 전환 깜빡임 0. 평균 휘도 변화가 0.5를 넘거나 8×8 블록 변화가 3을 넘으면(0~255 기준) 깜빡임으로 센다.
- 품질 전환 때 섀도 맵이 바뀌는 횟수 0.
- 낮밤 전환 중 한 프레임의 평균 휘도 변화는 8 이하.

0.5는 평균 휘도 130의 약 0.4%다. 수정 뒤 TAA 지터(0.15)보다는 크고 수정 전 품질 전환(1.55)보다는 작아서 이 값을 골랐다.

하네스는 프레임마다 화면을 읽어 오고, 품질이 바뀐 프레임이 두 임계값 중 하나라도 넘게 변했으면 깜빡임으로 센다.

```python
import numpy as np

def is_flicker(prev, cur, mean_limit=0.5, block_limit=3.0):
    """prev, cur: 3D 영역의 휘도(2D uint8), 카메라는 정지."""
    a, b = prev.astype(np.float32), cur.astype(np.float32)
    if abs(b.mean() - a.mean()) > mean_limit:
        return True
    h, w = (a.shape[0] // 8) * 8, (a.shape[1] // 8) * 8
    blocks = lambda x: x[:h, :w].reshape(h // 8, 8, w // 8, 8).mean(axis=(1, 3))
    return np.abs(blocks(b) - blocks(a)).max() > block_limit

flicker = sum(is_flicker(f[i - 1], f[i]) for i in tier_switch_frames)
```

그다음 같은 자세에서 설정을 하나씩 바꿔 봤는데, 이동 중 품질의 PCF를 PCSS로 되돌렸을 때만 큰 흰 얼룩이 사라졌다. 얼룩의 정체는 그림자를 꺼 둔 앞벽을 그대로 통과한 110,000 lux 햇빛이었고, PCSS에서는 우연히 가려졌을 뿐이었다. 빛이 벽을 뚫고 있었으므로 벽이 빛을 막도록 고쳤다.

품질이 바뀔 때 화면이 튀는 나머지 원인은 대부분 SSR이 켜졌다 꺼지는 데 있었다. 그 차이 하나만 없애도 전환당 평균 휘도 변화가 1.86에서 0.66으로 줄었고, 나머지는 PCSS, 섀도 맵 크기, TAA, 블룸 차이에서 왔다.

## 품질 설정 차이를 한곳에 모으기

이번에는 빛을 바꾸는 값이 두 품질 설정 사이에서 달라지지 않게 했다. 지금 두 설정은 AO 품질만 다르고, 그 차이도 작은 표 한 곳에만 둔다.

```cpp
struct Tier { filament::QualityLevel ao, aoFilter; };   // 허용된 차이는 이것뿐

Tier tierFor(bool moving) {
    using filament::QualityLevel;
    return moving ? Tier{QualityLevel::LOW, QualityLevel::MEDIUM}
                  : Tier{QualityLevel::HIGH, QualityLevel::HIGH};
}

void apply(filament::View* view, const Tier& t) {
    using namespace filament;
    AmbientOcclusionOptions ao;
    ao.bentNormals = true;                 // 가려진 곳에 IBL이 새지 않게
    ao.quality = t.ao;
    ao.lowPassFilter = t.aoFilter;
    view->setAmbientOcclusionOptions(ao);
    view->setShadowType(ShadowType::PCF);  // 두 단 공통
    ScreenSpaceReflectionsOptions ssr;
    ssr.enabled = false;                   // 두 단 공통
    view->setScreenSpaceReflectionsOptions(ssr);
    // TAA·bloom 켬, 동적 해상도 끔, 1024 그림자 맵도 두 단 공통
}
```

나머지 값은 두 설정에 공통으로 한 번만 지정한다. 앞벽은 이제 그림자를 드리우고, 창 유리와 창 너머 하늘 면만 그림자를 드리우지 않으므로 햇빛은 창으로만 들어온다. 창으로 들어온 햇빛 자리가 흰색으로 날아가서 해 세기도 110,000에서 50,000 lux로 낮췄다.

## 낮밤 전환과 검은 첫 프레임

낮밤 전환은 t = 0.5에서 프로브를 통째로 바꿨는데, 그 한 프레임에서 평균 휘도가 58이나 뛰었다. 지금은 디퓨즈 SH를 프레임마다 섞고 해 세기는 로그 공간에서 보간한다. 노출이 로그 단위이므로 선형으로 섞으면 전환 한가운데가 오히려 낮보다 밝아졌기 때문이다.

```cpp
float3 sh[9];
for (int i = 0; i < 9; ++i) sh[i] = daySH[i] * (1 - t) + nightSH[i] * t;
auto* light = IndirectLight::Builder()
    .reflections(t < 0.5f ? dayCube : nightCube)
    .irradiance(3, sh)
    .build(*engine);
scene->setIndirectLight(light);           // 직전에 섞은 것은 destroy
float sunLux = std::exp(std::lerp(std::log(daySun), std::log(nightSun), t));
```

목록 화면에서 방으로 들어갈 때 0.2초쯤 화면이 새까만 문제도 있었다. 호스트가 첫 프레임을 제출하자마자 화면을 보여 준 탓인데, 프레임을 더 그려 둬도 그대로였다. 첫 프레임의 GPU 시간을 받은 뒤에(끝내 오지 않으면 30장 뒤에) 화면을 보여 주게 하자 문제가 사라졌다.

시간에 따른 안정성 지표는 크게 좋아졌지만 화질 지표는 거의 그대로였고, 밤은 두 지표 모두 조금 나빠졌다. SSIM과 FLIP 임계값은 이번 측정을 보고 정했으므로 수정 전 값도 통과한다. 즉, 이 임계값은 화질이 나빠지는 회귀를 잡을 뿐이고 옮긴 결과가 Metal 버전과 같다는 근거가 되지는 못한다. 원래 목표(SSIM ≥ 0.95, FLIP ≤ 0.05)와는 아직 거리가 멀고, 그 차이의 큰 부분은 Metal 버전이 여러 리그로 베이크한 GI에서 온다.

안정성을 얻은 대가로 정지 화면 품질을 내줬다. 바닥과 탁자의 화면 공간 반사가 빠졌고 PCSS 소프트 섀도, 컨택트 섀도, 2048 섀도 맵도 빠졌다. 밤 창밖은 여전히 낮처럼 밝고 LED 띠의 빛도 벽에 번지지 않는데, 둘 다 라이트맵 작업에서 다룰 예정이다.

## 스크린샷을 믿기 전에 드래그부터 녹화하기

오프라인 Blender 장면은 무대처럼 만든다. 환경은 배경막이고 카메라가 밖에 서 있으니 벽 하나쯤 없어도 된다. 하지만 Filament는 IBL로 그 환경을 사방에서 오는 빛으로 다루고, 1인칭 카메라는 보는 사람을 상자 안에 세운다. 나는 장면을 있는 그대로 세 번 옮겼고, 옮길 때마다 드러난 구멍을 메웠다.

다음에도 챙길 것은 품질 설정이다. 성능 때문에 품질을 나눴는데, AO·섀도 필터링·SSR처럼 빛이나 그림자를 바꾸는 값이 두 설정에서 다를 때마다 움직일 때만 생기는 아티팩트가 나왔다. 하네스는 정지 프레임만 찍었기 때문에, 이틀 동안 나는 이미 제대로 나오던 유일한 상태만 비교하고 있었다. 다음 장면에서는 위의 품질 표를 첫 커밋에 넣고, 스크린샷을 믿기 전에 품질이 바뀌는 드래그 시나리오를 하네스로 녹화해 깜빡임 판정부터 돌릴 생각이다.
