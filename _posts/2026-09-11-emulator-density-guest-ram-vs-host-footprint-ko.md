`-memory 4096`으로 띄운 안드로이드 에뮬레이터 한 대가 호스트에서 상주 메모리를 4,605~5,457MB 썼다. 중앙값은 4,802MB였다. 용량 계획은 4096이라는 숫자로 세웠었다. 그래서 처음에는 호스트마다 에뮬레이터를 두 대씩 올렸다가 이 차이를 잰 뒤 한 대로 되돌렸다.

## GPU 없는 VM 열두 대

테스트 팜은 리눅스 VM 열두 대였다. 대마다 8코어에 메모리 12GB 남짓(`free -m` 기준 총 11,959MB)이고 GPU는 없다. VM마다 에뮬레이터를 하나씩 띄웠다. API 34 x86_64 이미지를 화면 없이 `-gpu software -memory 4096 -cores 3`으로 실행했다.

같은 열두 대에서 병렬 테스트 슬롯을 더 뽑고 싶었다. 테스트가 멀쩡한 채로 호스트 한 대에 에뮬레이터를 몇 대까지 띄울 수 있을까? 대당 3코어로 치면 8코어 머신에 두 대다. 메모리로 따져도 12GB에 4GB씩이면 두 대, 잘하면 세 대가 들어간다.

## 세 대와 네 대를 올려 봤다

처음엔 그냥 해 봤다. 호스트마다 두 대·세 대·네 대를 나눠 올렸고 대당 4096MB와 3코어는 그대로 뒀다.

네 대를 올린 호스트는 금방 쓰러졌다. 한 대는 11,959MB 중 11,477MB를 쓴 채 load average가 10.7이었고 qemu 프로세스 넷 중 하나는 이미 사라져 있었다. 다른 한 대에서는 OOM killer가 돌았고 load가 58까지 올랐다. SSH는 인증 전 배너 교환 단계에서 타임아웃이 나서 들어가 볼 수조차 없었다.

다음엔 에뮬레이터를 줄여서 끼워 넣었다. 세 대짜리는 3072MB·2코어, 네 대짜리는 2560MB·2코어로 잡았다. 이번엔 쓸 만한 데이터가 하나도 나오지 않았다. 내가 만든 헬스체크의 재시작 핸들러가 SIGTERM을 비동기로 보냈기 때문이다. 설정을 적용하자 그 호스트의 인스턴스가 전부 꺼졌고 정상 상태를 잴 틈이 없었다. 재시작 핸들러를 고치기 전에는 밀도 실험 데이터를 믿을 수 없었다.

제대로 도는 걸 본 구성은 4096MB·3코어 두 대뿐이었다. 그것도 호스트 한 대에서 두 인스턴스가 정상으로 보고된 정도였다. 아홉 대를 두 대 구성으로 바꾸고 세 대는 한 대로 남기자 슬롯이 12개에서 21개가 됐다. 근거는 유휴 상태의 헬스체크가 전부였다.

## 판정 기준부터 정했다

며칠 뒤 실험을 제대로 문서로 썼다. 두 인스턴스가 정상이라는 것만으로는 테스트가 나빠지지 않는다고 말할 수 없었다.

먼저 에뮬레이터를 띄우기 전에 밀도를 걸러내는 정적 게이트를 만들었다.

- 에뮬레이터 메모리 합은 호스트 메모리의 75% 이하
- 호스트 메모리는 최소 2GB 남긴다
- 에뮬레이터 코어 합은 호스트 코어에서 1을 뺀 값 이하

모든 에뮬레이터를 같은 스키마로 샘플링하는 읽기 전용 프로브도 붙였다. ADB 왕복 지연, 헬스 상태, qemu CPU와 RSS, 호스트 load, CPU·메모리 압력(PSI), 스왑, OOM 카운터, ANR 수를 모은다. 테스트가 돌고 있으면 성공 건수도 남긴다. 에뮬레이터를 띄우거나 멈추거나 죽이는 일은 하지 않는다.

리포트의 판정 규칙은 미리 못 박았다. 두 대 구성은 한 대 구성보다 테스트 성공률이 2%p 이상 떨어지거나 p95 지연이 50% 이상 늘면 탈락이다. OOM이 한 번이라도 나거나 메모리 압력이 임계를 계속 넘어도 탈락이다. 실제 테스트 트래픽 없이 돈 결과는 `idle-soak`으로만 기록하고 통과로 치지 않는다.

세 대 구성은 이 게이트에서 시작도 전에 떨어졌다. 3코어 x 3대면 9코어인데 게이트가 허용하는 건 7코어다. 남은 비교는 두 대 대 한 대였다.

## 두 대를 띄우면 700MB만 남았다

한 대짜리 대조군을 만들려고 두 대 구성이던 호스트 셋을 한 대로 내렸다. 그 이유를 인벤토리 주석에 적어 뒀다. 에뮬레이터 두 대를 띄우면 호스트 가용 메모리가 700MB대까지 떨어졌다. 그런 호스트로는 여유 있게 한 대만 도는 호스트를 대신할 수 없었다.

계산이 맞지 않았다. 4096MB 두 대면 8,192MB다. 11,959MB에서 빼면 3.7GB쯤 남아야 하는데 왜 700MB밖에 없을까? 계획이 세지 않은 무언가가 메모리를 쓰고 있었다.

## 열두 대 전부에서 qemu RSS를 쟀다

다음 날 열두 대 전부에서 에뮬레이터마다 qemu 프로세스의 상주 메모리를 쟀다. 게스트 메모리를 4096MB로 설정한 기준이다.

| | 에뮬레이터 1대의 호스트 RSS |
|---|---|
| 최소 | 4,605MB |
| 중앙값 | 4,802MB |
| 최대 | 5,457MB |

이런 에뮬레이터 두 대가 유휴 상태에서도 호스트 메모리의 81~89%를 차지했다. 부하가 걸리면 그 호스트들은 global OOM으로 죽었다.

늘어난 메모리는 두 군데서 나온다. qemu가 게스트 RAM 위에 자기 오버헤드를 얹는다. 그리고 `-gpu software`는 CPU로 렌더링해서 원래 GPU에 있을 프레임버퍼와 컬러 버퍼가 호스트 RAM을 잡는다. GPU가 없는 호스트라 피할 길이 없다.

## 게이트가 호스트 점유량을 세게 고쳤다

게이트가 두 대 구성을 통과시킨 건 게스트 RAM에 N을 곱했기 때문이다. 게스트 RAM에 에뮬레이터당 오버헤드(기본 1024MB)를 더한 호스트 점유량으로 판정하게 고쳤다. 두 값을 따로 출력해서 판정만 봐도 근거가 보이게 했다. 일반적인 이름으로 다시 쓴 검사는 이렇다.

```bash
#!/bin/bash
# usage: gate.sh HOST_MB HOST_CORES N GUEST_MB GUEST_CORES
host_mb=$1 host_cores=$2 n=$3 guest_mb=$4 guest_cores=$5
overhead_mb=${EMU_OVERHEAD_MB:-1024}   # qemu + software GPU buffers

per_emu_mb=$((guest_mb + overhead_mb))
need_mb=$((n * per_emu_mb))
reasons=""
reject() { reasons="${reasons:+$reasons,}\"$1\""; }

(( need_mb <= host_mb * 75 / 100 ))     || reject memory_budget
(( host_mb - need_mb >= 2048 ))         || reject memory_headroom
(( n * guest_cores <= host_cores - 1 )) || reject core_budget

echo "{\"n\":$n,\"per_emu_mb\":$per_emu_mb,\"need_mb\":$need_mb,\"reasons\":[$reasons]}"
[ -z "$reasons" ]
```

이 호스트의 숫자로 기본 오버헤드와 오버헤드 0을 한 번씩 돌리면 판정이 갈린다.

```console
$ ./gate.sh 11959 8 2 4096 3; echo "exit=$?"
{"n":2,"per_emu_mb":5120,"need_mb":10240,"reasons":["memory_budget","memory_headroom"]}
exit=1
$ EMU_OVERHEAD_MB=0 ./gate.sh 11959 8 2 4096 3; echo "exit=$?"
{"n":2,"per_emu_mb":4096,"need_mb":8192,"reasons":[]}
exit=0
```

N을 1에서 3까지 넣어 보면 예전 판정과 새 판정이 다른 줄은 N=2 하나다.

| N | 게스트 RAM만: 필요 / 여유 | 판정 | 오버헤드 1024MB 포함: 필요 / 여유 | 판정 |
|---|---|---|---|---|
| 1 | 4,096 / 7,863MB | 통과 | 5,120 / 6,839MB | 통과 |
| 2 | 8,192 / 3,767MB | 통과 | 10,240 / 1,719MB | 메모리 예산, 여유 |
| 3 | 12,288 / -329MB | 메모리, 여유, 코어 | 15,360 / -3,401MB | 메모리, 여유, 코어 |

11,959MB의 75%는 8,969MB다. 8,192는 그 안에 들어서 통과했고 10,240은 넘어서 떨어진다. 실제 게이트에서 N=2를 넣은 출력을 필요한 필드만 남기면 이렇다.

```json
{"eligible":false,"n":2,"avd_memory_mb":4096,"avd_memory_overhead_mb":1024,
 "avd_effective_memory_mb":5120,"memory_required_mb":10240,
 "memory_headroom_mb":1719,"reasons":["memory_budget","memory_headroom"]}
```

오버헤드를 0으로 두면 예전 판정이 그대로 나오는지 보는 테스트도 남겼다.

기본값 1024MB는 내가 잰 오버헤드의 중앙값(4,802 − 4,096 = 706MB)은 덮지만 최댓값(5,457 − 4,096 = 1,361MB)은 못 덮는다. 꼬리는 75% 상한과 2GB 여유 규칙이 받아 준다고 봤다. 기본값을 최댓값 쪽으로 더 넉넉하게 잡아도 됐다.

새 게이트에서는 이 호스트에 두 대 구성이 자격 미달이다. 모든 호스트를 한 대로 되돌렸다.

## 그룹 라벨이 계획서에서 왔다

버그가 하나 더 있었다. 실험 도구가 그룹을 잘못 나누고 있었다. 도구는 호스트를 "1대 그룹"과 "2대 그룹"으로 나눌 때 처음 계획대로 하드코딩한 호스트 이름 범위를 썼다. 실험군 아홉 대에서 두 번째 에뮬레이터를 내리자 전부 한 대 구성이 됐는데 매니페스트에는 여전히 2대 그룹으로 남는다. 리포트는 1대와 1대를 비교해 놓고 1대와 2대를 비교했다고 냈을 것이다.

그래서 인벤토리 항목의 에뮬레이터 수로 호스트마다 그룹을 정하게 바꿨다. 호스트별 밀도는 매니페스트에 기록한다. 세 대 이상은 그냥 넘기지 않고 거절한다. 뺄 호스트는 목록으로 명시하게 했다. 테스트 대상 앱이 소프트웨어 렌더러에서 크래시를 낸 호스트 두 대를 이 목록에 넣었다. 새로 만든 매니페스트는 1대 그룹 10대와 2대 그룹 0대, 제외 2대다. 실험군이 비어 있으니 리포트는 `missing_control_or_treatment`로 판정을 보류한다.

## 다시 호스트당 한 대

| 단계 | 답 | 근거 |
|---|---|---|
| 4096MB로 세 대·네 대 | 안 됨 | OOM, load 58, SSH 접속 불가 |
| 줄여서 세 대·네 대 | 데이터 없음 | 재시작 핸들러가 인스턴스를 전부 멈춤 |
| 4096MB로 두 대 | 됨, 슬롯 21개 | 호스트 한 대, 유휴 상태에서 두 인스턴스 정상 |
| 실제 점유량으로 두 대 | 안 됨, 슬롯 12개로 복귀 | 에뮬레이터당 RSS 4,605~5,457MB, 유휴 상태 호스트 메모리 81~89% |

팜은 호스트당 에뮬레이터 한 대로 남았다. 두 대를 돌리려면 VM 메모리를 늘리거나 에뮬레이터 메모리를 줄여야 한다. 어느 쪽이든 띄우기 전에 게이트가 먼저 따진다.

## 밀도 실험 전에 RSS부터

지금은 점유량부터 잰다. 에뮬레이터 한 대만 도는 호스트에서 qemu 프로세스마다 `ps -o rss`를 한 번 찍었으면 밀도 실험 전에 "4GB" 에뮬레이터가 4.6~5.5GB를 쓴다는 걸 알았다. 1분이면 되는 일이었다. `-memory 4096`은 게스트에게 주는 양이다. CPU로 렌더링하는 에뮬레이터에서는 호스트가 실제로 쓰는 양과 답이 바뀔 만큼 차이가 났다.

정작 아찔했던 건 그룹 라벨 버그다. 지금은 실험 그룹을 각 호스트가 실제로 보고하는 에뮬레이터 수로 만든다. 그룹이 비면 리포트가 결론을 내지 않게 한다. 에뮬레이터 밀도를 바꾸기 전이라면 `ps -o rss`부터 찍어 보길 권한다.
